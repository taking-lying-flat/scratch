# Casebook 技术分析写作

产出正式、准确、可复核的中文技术分析。文档应解释机制或证明故障根因，不以叙事感、宣传性或口语化表达替代证据。

## 确定文档任务

先确定唯一的主导类型，避免混写：

- 机制分析：回答组件如何协作、边界如何传递，以及设计为何成立。
- 故障分析：回答触发条件、错误传播路径、根因、修复与验证结果。

若任务实质上是教程、操作手册或 API 参考，不强行套用 casebook 结构。复现步骤和修复操作可以作为故障分析的局部章节，但不得打断主因果链。

## 建立证据链

写作前先核对涉及的仓库、提交、版本、配置和可复现现象。优先使用一手材料：源码、固定提交、issue、PR、官方文档、测试或日志。

- 每个关键结论都必须由源码路径、运行结果或明确推导支持。
- 明确区分事实、推导与假设。证据不完整时写明“根据 X 可推导”或“当前证据仅表明”，不得把推测写成事实。
- 不编造调用链、配置、日志、性能数据、源码行号或实验结果。
- 引用 GitHub 源码时优先使用包含完整 commit SHA 和行号范围的永久链接，避免指向会漂移的默认分支。
- 只摘取证明当前论点所需的最小代码片段；紧邻代码解释输入、状态变化、输出和对应结论。
- 修复建议必须对应已证明的根因，并说明它恢复了哪一条不变量。存在 producer 与 consumer 两侧防护时，分别说明职责。

## 组织论证

标题应包含明确对象与技术问题，避免悬念式、夸张式或营销式标题。

机制分析通常按以下关系展开：

1. 范围、版本与术语；
2. 核心不变量或 mental model；
3. 数据流、控制流或状态流；
4. 边界条件与组件接口；
5. 内核或底层实现；
6. 可验证结论与适用限制。

故障分析通常按以下关系展开：

1. 现象、影响范围与复现配置；
2. 从触发条件到最终故障的链路总览；
3. 按执行顺序展开每个状态转移；
4. 根因与被破坏的不变量；
5. 修复方案、验证结果与剩余限制。

结构服务于论证，不要求每篇文档机械包含全部章节。长文可增加目录；只有在版本、形状、职责或配置存在多字段对照时才使用表格。只有当顺序、所有权或边界关系用正文难以准确表达时才使用流程图或等宽文本图。

每节先给出本节主张，再给证据和解释。因果链使用明确关系：前置条件导致状态变化，状态变化破坏不变量，破坏结果触发可观测故障。不要用时间顺序暗示未经证明的因果关系。

## 使用书面化技术语言

- 使用客观、克制、可证伪的书面表达；默认不使用第一人称或直接称呼读者。
- 删除“我们先看”“可以看到”“很明显”“其实”“简单来说”“一眼就能看出”“踩坑”“玄学”“炸了”“搞定”等会话化措辞。
- 避免反问、感叹、悬念铺垫、情绪评价和无信息量的过渡句。
- 不使用“关键”“核心”“严重”“高效”“稳定”等空泛判断；必须同时说明具体对象、条件、后果或度量。
- 一个概念固定使用一个术语。首次出现时给出定义，随后保持中文、英文、大小写和代码格式一致。
- 标识符、参数、文件名、张量形状和短表达式使用反引号。普通技术名词不因强调而全部代码化。
- 区分描述性陈述与规范性陈述。仅在接口约束或正确性条件确实要求时使用“必须”“禁止”。
- 主动写明执行主体。例如写“consumer 读取负长度后计算错误索引”，不要写“随后出现了错误索引”。
- 中英文之间保持一致的空格风格；数字、单位、数据类型和张量维度必须完整。

## 使用 GitHub alerts

遵循 [GitHub alerts 语法](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#alerts)，只使用以下五种标记：

- `[!NOTE]`：补充实现背景、范围或不影响主结论的限制。
- `[!TIP]`：经过验证且能改善实施方式的建议。
- `[!IMPORTANT]`：理解论证所必需的不变量、前置条件或中心结论。
- `[!WARNING]`：需要立即注意以避免错误配置、错误结果或兼容性问题的信息。
- `[!CAUTION]`：可能导致数据损坏、死锁、安全风险或其他严重后果的行为。

重要不变量应优先使用 `[!IMPORTANT]`；已确认故障后果应根据严重程度使用 `[!WARNING]` 或 `[!CAUTION]`。每个 alert 只表达一个结论，并紧接必要解释。

Alerts 不是装饰。每篇文章通常限制为一至两个，不连续放置，不嵌套，不用 alert 代替正文论证。删除后不会影响读者正确理解或操作的信息，不应放入 alert。

```markdown
> [!IMPORTANT]
> `cu_seqlens` 定义逻辑序列边界；物理连续的地址本身不提供样本隔离。
```

## 呈现代码、数据与图示

- fenced code block 标注准确语言；非真实源码明确标注为“伪代码”或“简化表示”。
- 命令与输出分开，保留能够证明结论的上下文，不把预期输出伪装成实测结果。
- 对张量或缓冲区写明 shape、dtype、单位、索引域和边界语义；对并发代码写明线程、warp、CTA、stream 或进程的所有权。
- 对照表的列应具有可比较语义；不要把连续段落仅为视觉效果改成表格。
- 图示必须与正文使用同一命名，并在图后解释图示证明的结论。

## 管理引用与链接

- 结论后就近放置来源链接，不在文末堆积无法映射到具体主张的链接列表。
- 本仓库文件使用相对链接；外部链接使用有意义的描述文本，不使用裸 URL。
- 重命名文档或标题时，同步更新 README、目录、交叉引用和 heading anchor。
- 引用的源码行必须确实包含所述行为；若行为跨多个函数，分别链接入口、状态转换与消费位置。
- 第三方解释只能作为辅助材料，不能替代可获得的一手源码或官方文档。

## 完成前验证

交付前逐项检查：

1. 标题、范围和结论一致，文档没有偏离主问题。
2. 故障链或机制链不存在未解释的状态跳跃。
3. 每个关键事实均有证据，所有推导和不确定性均已标注。
4. 术语、标识符、版本、shape、dtype 和单位前后一致。
5. Alerts 的类型与严重程度匹配，数量克制且不连续。
6. 本地相对链接和 heading anchor 有效；外部源码链接指向正确版本与行号。
7. 代码块可读且语言标记正确，没有把伪代码或预期输出写成实测证据。
8. 删除口语、重复结论、空泛修饰和没有技术作用的段落。
9. 运行 `git diff --check`，并使用仓库可用的 Markdown link checker；若没有工具，至少解析并检查所有本地相对路径。

修改既有文档时保留作者已经证实的技术结论。发现结论与证据冲突时，先指出冲突并以可复核材料为准，不为追求文风统一而改变技术含义。
