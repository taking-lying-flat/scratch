# Casebook 写作编排

产出正式、准确、可复核且便于扫描的技术分析。每篇案例以问题为入口，完整讲授理解问题所需的可迁移背景，包括术语来源、数学或数据结构、执行模型及其与故障的连接；背景不得压缩成只够支撑结论的术语表。机制文档围绕组件关系、状态传递、边界条件和设计不变量展开；故障文档围绕现象、触发条件、错误传播、根因、修复和验证展开。标题直接标明对象与问题，开篇尽早给出范围和结论。

## 协作流程

先完成论证和正文，再读取并应用 [casebook-github-rendering](../casebook-github-rendering/SKILL.md) 设计 GitHub 原生呈现；需要独立网页时由该技能生成 GitHub Pages 前端。交付前读取并应用 [casebook-review](../casebook-review/SKILL.md)，修复其中发现的问题。小范围事实修改仍执行审校；纯链接维护无需重排全文。

## 论证与证据

每节先提出主张，再给出证据、推导和适用边界。每段围绕一个中心问题，在段内完成条件、机制、结果和证据的闭环；同一因果环节写成连续段落，避免把每句话拆成独立行、列表项或小节。列表仅用于严格并列的字段、步骤和检查项，表格仅用于多字段对照，图示仅用于正文难以清楚表达的顺序、所有权或边界关系。

写作前核对仓库、版本、配置和复现现象，优先使用源码、固定提交、issue、PR、官方文档、测试与日志。关键结论需要直接证据或明确推导；证据不足时标注推断范围。不得编造调用链、源码行号、日志、数据或实验结果。源码链接使用完整 commit SHA 和准确行号，代码片段只保留证明当前主张所需的部分，并解释输入、状态变化、输出及其证明作用。修复方案应对应已确认的根因，并说明恢复了哪条不变量。

## 文风

使用客观、克制、可证伪的书面语，明确写出执行主体、约束条件和具体后果。禁用否定—转折模板（`不是……而是……`、`……而不是……`），直接陈述正向结论，再单独说明排除条件。删除“我们先看”“可以看到”“很明显”“其实”“简单来说”“一眼就能看出”“踩坑”“玄学”“炸了”“搞定”等会话化措辞，避免反问、感叹、悬念铺垫和空泛修饰。术语首次出现时定义，后续保持中文、英文、大小写与代码格式一致；标识符、参数、文件名、shape、dtype、单位和索引域必须准确。
